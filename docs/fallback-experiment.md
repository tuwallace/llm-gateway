# Experiment: a concurrency limit and a second node for the shared fallback

**Question.** Neither caps nor a dedicated pool protect anyone once every primary node is down:
the single llama3 fallback then serves all teams, and in phase C of the simulation 8 to 13
requests time out. Does a concurrency limit on the fallback deployment, a second fallback node,
or both fix that?

**Short answer.** No. The limit turns slow timeouts into fast failures by serving almost nothing,
and it makes the fallback **shut itself off for 30 seconds** whenever it trips. A second node alone
changes nothing measurable. Neither touches the noisy-neighbour problem in normal operation.

**Follow-up (below): a fallback with capacity comparable to the primaries does fix it** (0 failures in
the run, against 15 and 17 for the baselines), and a shorter cooldown removes the limit's blackout cost.

## What the limit does

`max_parallel_requests` on a deployment (`litellm_params`) is a router-level limit on concurrent calls
to that deployment. Probed with all primaries stopped and 8 simultaneous requests at a limit of 2:

- 3 succeeded; 5 failed with HTTP **500** after 9-10 s, quoting the *primary's* connection error
  (the real cause, `RateLimitError: Deployment has all max_parallel_requests slots in use`, is only
  in the gateway log).
- Tripping the limit puts the deployment into the router's **30 s cooldown**. An idle fallback then
  answered 429 at 1, 10 and 20 s after the burst and 200 again at 35 s. A busy spell becomes a blackout.
- With both levers (limit 2 on each of two nodes), a burst of 8 served 4 (2 per node), rejected 4,
  and both nodes tripped together: 429 one second later.

## Method

Same simulation as before (`simulate.py`, 210 s, five team profiles, node failures in phases B and C).
Variants are generated by `experiments/make_fallback_config.py` from the main config:

| Run | Fallback configuration |
|---|---|
| 1, 8 baseline | one llama3 node, no limit (two independent runs, for the spread) |
| 5 limit | one node, `max_parallel_requests: 2` |
| 9 node2 | two nodes (11438, 11439), no limit |
| 10 both | two nodes, limit 2 each |

**Cache hygiene (important).** The first attempt at runs 6 and 7 looked like a big win for the second
node. It was not: runs that start within 10 minutes of another inherit its cached answers (hit rate
83-90% against 75-78% cold), so they have far less uncached work. The simulator now flushes the
semantic cache before every run (`--keep-cache` to opt out) and `compare_runs.py` prints the hit rate.
Everything below is from cold-cache runs; the warm runs are discarded. See "Corrections".

## Findings

1. **The limit trades timeouts for fast failure, not for service.** Phase C timeouts went from 11-13 to
   0, but "both" answered no uncached request at all in phase C (baseline: 4) and rejected 29 requests
   (baseline: 11-13). The failure total (timeouts plus 5xx) fell from 15-17 to 5, but that count leaves
   out the extra rejections (429s), and no more requests succeeded. Failing in 0.1 s instead of hanging
   for 60 s is arguably kinder to callers; it is not protection.
2. **The limit adds failures in normal operation.** With one primary down (phase B), some requests spill
   to the fallback, trip the limit and send it into cooldown: limit-only had 10 failures in B (7 of them
   500s), "both" had 4. The quiet team was hit too (support: 2 and 9 rejections, against 0).
3. **A second node alone does nothing measurable.** Phase C timeouts 10 against 11-13 and uncached
   latency 38 s against 41-43 s. Demand in phase C (a research burst of 20 requests of 200 tokens, plus
   everyone else's uncached traffic) is far beyond what two single-slot llama3 nodes can serve.
4. **None of this affects the noisy-neighbour effect**, as expected: support's tail outside phase C
   stayed around 28-56 s in every variant here. These levers address failover only.
5. **Error reporting is poor.** Deployment-limit rejections surface as a 500 quoting a different node's
   connection error, and cooldowns surface as 429, so a client or dashboard cannot tell "overloaded"
   from "broken".

## Follow-up: capacity-matched fallback and a shorter cooldown

The first round suggested the fallback simply lacked capacity. Tested directly (cold cache, one run each):

| Run | Fallback |
|---|---|
| 12 big fb | three phi3 standby nodes (11439-11441), no limit, cooldown 30 s |
| 13 big+limit+cd5 | the same three nodes, `max_parallel_requests: 2` each, `cooldown_time: 5` |
| 14 single+limit+cd5 | the original single llama3 node, limit 2, `cooldown_time: 5` (compare run 5, same but cooldown 30) |

**Why phi3 standby nodes, not llama3.** llama3 is about twice as slow per token, so matching the
primaries' capacity would take roughly six llama3 nodes (about 30 GB), which this machine cannot hold.
Three phi3 nodes are the same capacity as the primaries (probe: 12 simultaneous 120-token requests took
19.6 s through the primaries and 20.0 s through the standby pool). This tests *capacity*, not model
diversity. Standby nodes unload after 20 s idle, so six phi3 copies are never resident together.

### Follow-up findings

1. **Capacity is what was missing.** With a standby pool the size of the primaries, the run had no
   timeouts or errors in any phase, phase C uncached answers rose from 4 to 9, and their latency halved
   (19.5 s against 41-43 s). It is still slow because the same load that makes the primaries queue now
   sits on equal capacity: the outage is absorbed, not made fast.
2. **It also absorbs the spillover in phase B.** With one primary down, the standby nodes answered 12
   uncached requests (the baseline's single llama3 answered 13 in the second baseline run and then timed
   out on some). This is the same "fallback used while healthy primaries existed" pattern noted earlier
   (13 and 12 requests); its cause is still unknown, but it stops costing failures once the fallback has
   room.
3. **A shorter cooldown removes the limit's blackout cost.** Same single-node limit, cooldown 30 s -> 5 s:
   phase B failures fell from 10 to 0, phase C uncached latency from 12 s to 3 s, and uncached answers in
   C rose from 2 to 7. The limit still converts overload into 500s (3 to 6 per run), so it buys latency
   with failures: with the big pool, no limit gave 0 failures at 19.5 s, the limit gave 3 failures at 9 s.
4. **Quiet-team latency during bursts is not fixed by any of this.** Support's tail stayed 27-55 s;
   runs 13 and 14 look better (14.9 and 1.6 s medians) but are single runs, show 27-31 s p95s, and are far
   from the dedicated pool's 1.3 / 2.4 s. Do not read isolation into them.

### Follow-up caveats

- One run per configuration (the two baselines differ by 2 failures, 15 against 17; the big-pool run's 0 is
  outside that spread, the 3 and 6 are inside the noise of each other).
- The machine was swapping (4.6 GB of its 6 GB swap file in use when checked afterwards); cannot be
  attributed to these runs, but latency figures everywhere are indicative only.
- The standby pool costs three more nodes (about 11.4 GB when all are loaded) to cover a failure that is
  rare; they idle at almost no cost thanks to the 20 s keep-alive.
- `cooldown_time` is global in this config, so runs 13 and 14 also changed it for the primaries; the
  effects seen are in the fallback path.

## Corrections to earlier experiments

Runs 2 and 3 (caps) and the first full simulation started within the cache's 10-minute lifetime of the
previous run (gaps of 7, 8 and 6 minutes), so they were partly warm. Cold re-run of the caps
configuration (run 11):

| Caps | warm run 2 (earlier report) | cold run 11 |
|---|---|---|
| support during a research burst, p50 / p95 | 0.9 / 1.0 s | **1.2 / 40.2 s** |
| support otherwise, p50 / p95 | 1.0 / 1.2 s | 0.9 / 1.5 s |
| research ok / sent | 40 / 192 | **23 / 190** |
| research uncached tokens | 1,133 | **3,834** |
| client timeouts | 0 | **10, all in phase C** |

The conclusions of `concurrency-experiment.md` stand (caps protect the quiet team in normal operation,
starve the noisy team through the 2x RPM charge, and are bypassed during failover); the "0 timeouts"
and the 1.0 s p95 were warm-cache luck, and the failover bypass shows up here as 10 timeouts in phase C.
The dedicated-pool run (4) and the baselines (1, 8) were cold, so `dedicated-pool-experiment.md` stands
apart from its caps columns. The first full simulation followed a dry run by 6 minutes (hit rate 81%
against 75-78% cold): a mild inflation that does not change its conclusions.

## Recommendation

- **To absorb total primary failure, give the fallback capacity comparable to the primaries.** It was the
  only change that removed the failures (run 12). Size standby capacity to the load you must keep
  serving in an outage, and accept that it costs idle nodes.
- **A fallback concurrency limit is optional and has a price.** If fast failure is preferred to slow
  success, use a limit, but pair it with a short `cooldown_time` (5 s worked; 30 s caused a blackout
  and extra failures in normal operation).
- **A second fallback node on its own is not worth it**, and none of these changes address the
  noisy-neighbour effect: use the dedicated pool for that (`dedicated-pool-experiment.md`).
- Still untested: a llama3 (different-model) fallback at full capacity, repeated runs for variance, and
  shedding at the team level.

## Reproduce

```bash
gateway-env/bin/python experiments/make_fallback_config.py --limit 2 --out experiments/litellm_config.fb-limit.yaml
gateway-env/bin/python experiments/make_fallback_config.py --second-node --out experiments/litellm_config.fb-node2.yaml
gateway-env/bin/python experiments/make_fallback_config.py --limit 2 --second-node --out experiments/litellm_config.fb-both.yaml
CONFIG=experiments/litellm_config.fb-both.yaml ./restart_gateway.sh --reset
gateway-env/bin/python experiments/make_fallback_config.py --standby 3 --out experiments/litellm_config.fb-big.yaml
gateway-env/bin/python experiments/make_fallback_config.py --standby 3 --limit 2 --cooldown 5 --out experiments/litellm_config.fb-big-limit-cd5.yaml
gateway-env/bin/python experiments/make_fallback_config.py --limit 2 --cooldown 5 --out experiments/litellm_config.fb-limit-cd5.yaml
gateway-env/bin/python simulate.py --label "10 fb both (cold)"   # flushes the semantic cache first
# back to normal:
./restart_gateway.sh --reset
```
